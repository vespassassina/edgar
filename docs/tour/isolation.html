Everything before this milestone decided whether something may run. This one is about what happens while it runs: a subagent that may write gets a copy of the tree to write in, and a shell command gets the operating system's own walls around it. Neither half invents a policy. The worktree moves the working directory, which is an input the permission engine already reads; the sandbox is handed a decision the permission engine already made. Both fail loudly rather than quietly doing less than they promised, which is the only interesting design constraint on this page.

Stage 1. A tree of its own about 15 minutes

1A worktree per subagent

agents/worktree.py, agents/spawn.py

Look for: create finish Worktree _closed

The whole mechanism is one line in spawn(): session.cwd = tree.path. Everything else follows from it for free, because ToolContext.cwd comes from Session.cwd, and Guard.check rebuilds its Policy around that cwd on every single call. So the hard rule that a path outside the working directory is an Ask now points at the worktree, and the parent's files are outside it. The isolation is not a new rule; it is the old rule aimed somewhere else.

A worktree is cut from HEAD, the parent's last commit. A human who is halfway through an edit when a subagent starts is therefore never at risk: the subagent cannot see that edit and cannot touch it. That is worth knowing before you trust it, and it is the reason the test for it is named after the fact rather than after the function.

The two refusals are the point of the file. Outside a git repository there is no worktree to make, so create returns a refusal and the agent does not run at all — never a quiet fallback to sharing the tree, because an agent whose author asked for isolation and silently did not get it is worse than one that fails. And finish never passes --force, to git or to anything: if git status --porcelain shows anything at all, the worktree is kept, its path and branch go in the summary, and the line telling a human how to delete it goes there too. The harness will leave a directory lying around before it will throw away work it did not write.

Note where that summary goes: appended to the tool result, which is both what the model reads next and what the human sees in the transcript. There is no second channel and no log file to remember to check. If you learn about a kept worktree a week later, it is because you scrolled back to the call, or because git worktree list and git branch still show it.

Take with you: the cheapest isolation is the one that reuses a variable the rest of the system already reads. Adding an isolated flag to the permission engine would have been a second mechanism to keep correct forever; moving cwd was one assignment.

Stage 2. The platform's own walls about 25 minutes

2The Sandbox port, and the backend that does nothing

sandbox/base.py, sandbox/none.py, permissions/policy.py, cli/doctor.py

Look for: Sandbox wrap available backend best network_allowed

The port is one pure function. A backend does not run your command; it says what argv would run it confined, and run_argv — the one place in edgar that starts a subprocess, and the one place that knows how to kill a process group on Ctrl-C — starts that instead. The Blueprint's first sketch gave the protocol an async run(...). Turning it into wrap(...) -> list[str] bought two things: there is still exactly one launcher, and a command line can be asserted on a machine that cannot run it. That second one matters more than it sounds. A sandbox you cannot test is a sandbox you are trusting on faith, and most of what can go wrong with one is a wrong flag.

none.py is sixteen lines that accept every argument and ignore all of them. It is the default, and naming it in the config is how you say out loud that you are not sandboxed. The alternative — letting sandbox silently mean "whatever is installed" — is the failure mode this whole milestone is written against.

Two functions carry the honesty. backend(name) raises if the configured backend is unknown or merely absent, so a machine without bwrap fails to start a session rather than running everything unconfined under a config that says otherwise. best() walks the list backwards and returns the strongest backend that is really here; edgar doctor prints it next to what you have configured, as advice. It never changes the setting. Humans widen, machines tighten, and quietly turning a sandbox on is still a machine changing policy.

Then network_allowed(mode, tainted), which lives in permissions/ and not here on purpose. A backend enforces a decision; it must never make one. The answer is computed by the permission engine, fresh for each call because taint can be set by an earlier call in the same turn, carried on ToolContext.network, and handed to the backend as a boolean. There is exactly one direction of travel, and a test asserts the sandbox is never looser than the engine.

Take with you: a port that returns data instead of performing an effect can be tested everywhere, by everyone, on every platform. Pick that shape whenever the effect is the part you cannot reproduce.

3bubblewrap and seatbelt

sandbox/bwrap.py, sandbox/seatbelt.py

Look for: Bubblewrap Seatbelt profile

Fifty lines for both platforms, because neither file implements a sandbox — the kernel and the OS already did. Each one translates the same three facts (the command, the directories the harness says are writable, the network answer) into the local dialect.

On Linux that dialect is an argv: bind the whole filesystem read-only, bind the named roots back in writable, give it a fresh /tmp, and add --unshare-net when the answer was no. On macOS it is a small Lisp — (allow default), then (deny file-write*), then one (allow file-write* (subpath …)) per root, in that order, because later rules win in SBPL. Read the two files side by side and the shape is the same sentence twice.

Two details are worth stopping on. The seatbelt profile goes in the argv rather than a temporary file: nothing is left behind, and there is no window in which another process could swap the file between writing it and running it. And the writable set is built by the harness, from cwd and the blob directory — never from anything the model said. A tool argument cannot widen it, because it never reaches it.

Now the uncomfortable part, stated plainly because a tour that hides it is worse than no tour. This is a write and network boundary, not a read boundary. A confined command can still read your whole filesystem. That is what the Blueprint designed and what these twenty-five lines each do; the roadmap line for this milestone also said "cannot read outside the allowed roots", which these backends do not deliver. The contradiction is recorded in the ADR rather than papered over, because a sandbox that is believed to do more than it does is the exact failure this milestone exists to avoid.

Take with you: when the spec and the implementation disagree about a security boundary, the honest move is to ship the narrower claim and write down the gap. Nobody is hurt by a boundary that is smaller than advertised; everybody is hurt by one that is believed to be larger.
