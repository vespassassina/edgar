Everything before this milestone decided whether something may run. This one is about what happens while it runs: a subagent that may write gets a copy of the tree to write in, and a shell command gets the operating system's own walls around it. Neither half invents a policy. The worktree moves the working directory, which is an input the permission engine already reads; the sandbox is handed a decision the permission engine already made. Both fail loudly rather than quietly doing less than they promised, which is the only interesting design constraint on this page.

Stage 1. A tree of its own about 15 minutes

1A worktree per subagent

agents/worktree.py, agents/spawn.py

Look for: create finish Worktree _closed

The whole mechanism is one line in spawn(): session.cwd = tree.path. Everything else follows from it for free, because ToolContext.cwd comes from Session.cwd, and Guard.check rebuilds its Policy around that cwd on every single call. So the hard rule that a path outside the working directory is an Ask now points at the worktree, and the parent's files are outside it. The isolation is not a new rule; it is the old rule aimed somewhere else.

A worktree is cut from HEAD, the parent's last commit. A human who is halfway through an edit when a subagent starts is therefore never at risk: the subagent cannot see that edit and cannot touch it. That is worth knowing before you trust it, and it is the reason the test for it is named after the fact rather than after the function.

The two refusals are the point of the file. Outside a git repository there is no worktree to make, so create returns a refusal and the agent does not run at all — never a quiet fallback to sharing the tree, because an agent whose author asked for isolation and silently did not get it is worse than one that fails. And finish never passes --force, to git or to anything: if git status --porcelain shows anything at all, the worktree is kept, its path and branch go in the summary, and the line telling a human how to delete it goes there too. The harness will leave a directory lying around before it will throw away work it did not write.

Note where that summary goes: appended to the tool result, which is both what the model reads next and what the human sees in the transcript. There is no second channel and no log file to remember to check. If you learn about a kept worktree a week later, it is because you scrolled back to the call, or because git worktree list and git branch still show it.

Take with you: the cheapest isolation is the one that reuses a variable the rest of the system already reads. Adding an isolated flag to the permission engine would have been a second mechanism to keep correct forever; moving cwd was one assignment.
