Stage 1. The spine about 45 minutes

These four files are the whole system in miniature. Everything else is detail hanging off them.

1The loop

core/loop.py

Look for: run_turn _Turn _start _ask _run_tools _check Runtime

The file opens with the whole turn as pseudocode, and run_turn follows it step by step, numbered 1 to 10 in the comments. The diagram uses the same numbers. Each step with any detail is a helper one level down; no helper calls another, and nothing recurses.

flowchart TD
    start(["1 · record the prompt"]) --> safe["3 · safe point:
pause, /steer"]
    safe --> caps{"4 · over a
cost cap?"}
    caps -->|yes| budget(["budget_exceeded"])
    caps -->|no| ask["5 · ask the model
_ask"]
    ask --> calls{"6 · tool
calls?"}
    calls -->|yes| run["run them in order
_run_tools"] --> safe
    calls -->|no| steer{"7 · steer
pending?"}
    steer -->|yes| safe
    steer -->|no| acted{"8 · changed
something?"}
    acted -->|"no, or no check"| done(["9 · completed"])
    acted -->|yes| check["run the check
_check"]
    check -->|passed| done
    check -->|"failed, tries left"| safe
    check -->|"failed, none left"| failed(["verification_failed"])

There are four ways out: budget_exceeded, completed, verification_failed, and a cancel, which raises. On a cancel, seal() first gives every open tool call a result, so the transcript stays valid.

Take with you: the safe point (step 3) is the only place a pause or a /steer takes effect. The previous round always ended on a complete call-and-result pair, which is what keeps the transcript valid (stop 16).

2The vocabulary

core/message.py

Look for: Message TextBlock ToolUseBlock ToolResultBlock ErrorRecord ThinkingBlock

These are the shapes the model sees. The comment at the top shows a whole conversation written in these types. Everything is frozen: compaction builds new transcripts rather than editing old ones. A failed tool call is a ToolResultBlock with is_error set, never an exception.

4Done means verified

core/verify.py

Look for: verify Check

This is the smallest important file in the repository. When the model stops after changing something, the declared check runs. If it fails, its output goes back to the model while attempts remain. Decide for yourself whether it is as strong as the README claims.

Stage 2. The hands about 45 minutes

How the loop touches the world: where "the model asked" turns into "the thing happened".

5The tool contract

tools/base.py

Look for: Tool ToolSchema ToolContext ToolResult builtin_schema

A tool is a schema plus an async run. The schema's category (read, write, shell, network) is what the permission engine reasons about. Every built-in tool builds its schema through builtin_schema, which closes the object to the properties it names.

6The pipeline

tools/execute.py

Look for: execute _validate _failed

Every call from every source takes this one path, so this is the single place where a check on every tool call can sit.

7The decision

permissions/policy.py

Look for: decide _decide _mode Policy Allow Deny Ask

One pure function: no I/O, and the first match wins.

When nobody is there to answer, decide turns an Ask into a Deny with needed_prompt set, and edgar -p exits 5. Taint is sticky: once a tool returns content from the network, auto mode asks before shell and network calls for the rest of the session. The link-local check sits in the same hard layer as catastrophic commands, so it holds even in yolo: a URL that literally names 169.254.169.254 or another link-local address, the range every major cloud serves its instance-metadata endpoint on, is denied before anything else runs. It only catches a literal address, not a hostname that resolves to one (ADR-0049).

8The asking

permissions/guard.py permissions/matcher.py

Look for: Guard subject CATASTROPHIC credential inside link_local

The I/O half that keeps decide pure. Guard works out what a call touches, builds the Policy, asks you when the answer is Ask, and remembers your "always" answers. The matcher holds the list of commands that never run, the detection of credential paths, and link_local, which reads a URL's host as a literal IP address and checks it against 169.254.0.0/16 and fe80::/10.

This turns a CLI or an API into a tool with config alone. A command tool is an argv template and never a shell string. An HTTP tool has its host fixed and takes secrets only from the environment.

12Four vendors, one adapter

providers/openai_compat.py providers/quirks.py

Look for: OpenAICompatible Quirks QUIRKS connect Minted

OpenAI, Azure, OpenRouter, Ollama and any compatible server share one adapter. How they differ is a table of data, not branches in code. Check whether the table earns the claim: even what a provider can do (its context window, reasoning, parallel calls) is read off its row by HttpAdapter, never its name.

connect finds the credential before any request: a key from the environment, or else a token printed by a command the user named, such as gcloud auth print-access-token. That is how Azure without keys, Vertex AI and Bedrock sign in, with no cloud SDK. Minted runs the command again when its token is ten minutes old. Notice that the loader refuses the command in a project's config, and ask why.

13The one that needed its own adapter

providers/anthropic.py

Look for: Anthropic

Ask yourself why this one needed its own adapter, specifically. Follow how thinking blocks, their signatures and cache breakpoints travel.

14When the model gets it wrong

providers/repair.py providers/routing.py

Look for: text_call arguments select_model

Small local models fence their tool calls or write them as plain JSON; the repair recovers them deterministically and never invents a call. Routing in Core is a pure function that binds roles to models. It never picks a model you did not name. v1 (stop 22) adds declarative [[route]] rules ahead of that binding, same first-match-wins shape as permissions.decide(), still a pure function with zero cost.

Skip these on a first pass: pricing.py, registry.py, fake.py, http.py.

17Sessions on disk

storage/transcript.py core/session.py core/cancel.py

Look for: Log replay Session seal chain

A session is recorded as JSONL, append-only, never rewritten. Undo, compaction and cancel each append a record, and replaying the file rebuilds the exact view. Check that the append-only claim holds everywhere, including for a cancel and for /undo.

A fork (v1) keeps the rule: it is a new file whose second line names its parent and a turn, and chain reads the parent's lines up to that turn, then the fork's own, with a loop rather than recursion. save is the opposite move, the chain as one file that travels, with spilled output read back in and every string passed through memory/redact.py.

18The surface

cli/repl.py cli/slash.py cli/oneshot.py cli/render.py cli/setup.py cli/statusbar.py config/load.py

Look for: Shell dispatch run_prompt Renderer Status

This is where the size goes. Skim it; do not study it. One thing worth noticing: Status rebuilds itself from nothing but the event stream, same as the renderer, and since every event carries depth and agent_id, a concurrently running subagent (stop 22) gets its own row under the main one rather than interleaving into it (SUB-9). runtime() here is also where a model with no tool support is refused before the first prompt is sent, not on its first tool call (ROUTE-6, stop 22).

Stage 6. The know-how about 10 minutes

19Skills

skills/discovery.py tools/builtin/skill.py

Look for: discover split Found SkillTool

A skill is a folder with a SKILL.md, in the same format Claude uses. At startup only its frontmatter is read, so the prompt carries one line per skill (skill_index in context/builder.py); the body loads when the model calls the skill tool. Notice the order in discover: the project beats the user, and anything a human wrote beats anything learned. A skill is instructions, never code that runs: a script it bundles goes through the shell tool and its permission check like any other command.

By the end of Core you should be able to answer three questions without the docs open. What happens in a turn, step by step? Where does every tool call pass, and what can stop it there? How does a long session stay valid as it is compacted, cancelled and resumed? Any file you could not follow is a readability bug: open an issue.

Stage 7. The rest of it reference, dip in as needed

Six stops that finish the map of Core. Nothing here is on the critical path of a turn, which is why it comes last — but every file in src/edgar is now named by some stop on this tour, and a test fails if one stops being.

20Errors that stop, and a question that does not

core/errors.py core/aside.py

Look for: EdgarError ContextOverflow VerificationFailed Cancelled ask request

errors.py is the whole taxonomy in under thirty lines, and each class carries the exit code it produces [CLI-10]. The rule it encodes is the one from stop 6: a tool failure never raises, it goes back to the model as an error result. These are only for what the harness cannot proceed through — a budget spent, a context that will not fit even pinned, a verification exhausted.

aside.py is /btw [CLI-24, ADR-0028]: a side question that never touches the conversation. request is the interesting half — it takes the request the turn would have sent and cuts it back to the last complete unit, so the aside never ends on unanswered tool calls, which is the pairing invariant again. It shares the cached prefix and sends no tools, and its deltas go to a private bus so the turn in progress keeps the screen.

21The schema is the config

config/schema.py permissions/control.py

Look for: Config SECTIONS TABLES LATER ProviderSection PermissionsSection control_files is_control _TREES

Every key edgar accepts is a dataclass field here: the type hint is the validation rule and the default is the default, so "what does this key take" has exactly one answer to read [CFG-3]. Validation itself is hand-written in load.py rather than delegated to a library — that is the dependency budget again (ADR-0019), and it is what lets a message name the file, the key and the expected type. LATER is worth finding: keys that belong to a tier not built yet are known and ignored, so a config written for v3 does not error on v1.

control.py is thirty-five lines that decide which files steer edgar itself — the prompts, agents, tools, extensions and skills trees, plus config.toml and its siblings. Writing or editing one is Ask in every mode but yolo [PERM-12], because a model that can rewrite its own instructions can widen its own policy, and only a human may do that (ADR-0021).

22The prompt file, the counting, and the spill

context/prompts.py context/tokens.py tools/spill.py

Look for: Prompt load_prompt choose_profile COMPACT_BELOW SHIPPED approx_tokens CHARS_PER_TOKEN Spilled spill

The system prompt is a file, not a string in the source [CTX-16, ADR-0023]. A project may ship its own, and because it is a control file the model cannot change it without asking. choose_profile is the one piece of behaviour: below COMPACT_BELOW a smaller model gets the shorter prompt [PRV-17].

tokens.py is twenty lines and honest about it: four characters to a token, used for the compaction thresholds, with exact counts coming from the providers. Read CHARS_PER_TOKEN and then decide whether the approximation can hurt you — the answer is in which direction compaction errs.

spill is stage S0 of the context pipeline [TOOL-4, CTX-13]. Output over the limit keeps its head and its tail, and the whole text goes to a blob the model can read with an offset, so nothing is lost, only kept out of the prompt. Thirty lines, and the reason the session file never has to be compressed.

23Which tool wins a name, and what outlives the session

tools/registry.py storage/db.py

Look for: ToolRegistry core_registry registry_for cost _defers exposed Store SCHEMA grant trusted spend

registry.py answers two questions. Which tool wins a name: sources are added lowest priority first — built-ins, the skill tool, MCP, user, project — and a replacement is reported, never silent [TOOL-9]. And which schemas a request can afford: cost adds them up, and over tools.schema_budget the MCP ones are deferred behind tool_search [TOOL-15]. That is the mechanism the MCP page builds on.

db.py is the only SQLite in Core: grants, trust, each day's spend and each MCP server's cached tool list [PERM-6, PERM-13, BUD-2, TOOL-8]. Two files, and which is which is a decision worth reading — grants are the project's, in .edgar/edgar.db; trust and spend are yours across projects, in ~/.edgar/edgar.db. Never a config file, because config is what a human edits and these are what the machine records. WAL mode, short transactions and a busy timeout, because the folder may be under a sync client, and the file is created only when there is something to store.

24What the adapters share

providers/http.py providers/fake.py providers/pricing.py

Look for: HttpAdapter RETRYABLE Retry TIMEOUT events tool_calls error_message FakeProvider _rules cost_of BUILTIN CHECKED

http.py is the biggest file in providers/ and holds everything the two real adapters would otherwise each get slightly wrong: the request and its retries, server-sent events, error mapping, token counting and tool-call assembly. events and tool_calls are where a streamed response becomes whole blocks — the place to look when a provider's stream is fragmented differently from everyone else's. It is imported only by the adapters, so httpx never loads on a run that reaches no provider [PRV-4, NFR-1].

fake.py is the model that runs nowhere: three fixed rules, offline and deterministic, so edgar does something useful before you have a key and so almost every test in the suite can drive the real loop without a cassette (ADR-0009).

pricing.py is thirty-five lines with one opinion in them: unknown pricing is None, shown as "unknown", never a wrong zero [BUD-1, BUD-5]. A cap that silently counts nothing is worse than one that admits it cannot count. CHECKED dates the shipped table, and a [pricing] entry in config wins over it.

25The command line

cli/main.py cli/admin.py cli/models.py cli/trust.py edgar/__main__.py

Look for: main build_parser ADMIN USAGE command describe pick ROLES trusted digest executable

Read main.py with invariant 3 in your hand: nothing heavy may be imported at module level, because this module is on the path of every run and tests/e2e/test_startup.py fails the build if httpx, rich, prompt_toolkit, jsonschema, yaml, keyring or any edgar.providers module is pulled in (NFR-1, ADR-0012). The run paths are imported inside main(). __main__.py is three lines so that python -m edgar and the console script are the same program.

admin.py collects the subcommands that look at a project rather than run a turn, and each is one branch of command(): read what is on disk, print it, return an exit code. None of them contacts a model. Only trust, revoke and sessions rm change anything, and each changes only what it names.

models.py is edgar models list and the picker [CLI-30, ADR-0034]. describe prints where prompts would go — every provider, its endpoint, whether its key variable is set — without contacting anything [PRV-15], and pick is the sensible-defaults rule made concrete: Enter saves the choice for every project, p for this one, n for neither.

trust.py is why a cloned repository cannot run code on launch [PERM-13, CLI-19]. The executable parts of project config — command and HTTP tools, a verify.command, an [mcp.NAME] server, hooks and extensions — run only once the project is trusted. Trust is keyed by the project's path and a digest of that config, so changing what would run asks again.

26Memory and session search

memory/store.py memory/recall.py tools/builtin/memory_tools.py

Look for: add confirm _Op pinned Fts5Retriever Remember

M7 has a tour of its own: Memory, four stops on the boundary, recall, the markdown round trip, and forks and saves. What to carry from here: an active fact comes only from text a human typed, the model's own remember call makes a pending fact, and a pending fact is never in the prompt and never in the search index. A fact's text never changes — every confirm or forget is a status change under one operation number, which is why edgar memory undo can always put it back. The pinned set is chosen once at session start, above the cache breakpoint, so a fact added now shows from the next session.

27MCP

tools/mcp/client.py tools/mcp/schema.py tools/builtin/tool_search.py

Look for: Server discover McpTool to_schema ToolSearch

M8 has a tour of its own: MCP and signing in, four stops on the lazy start, deferred schemas and the loopback dance. What to carry from here: an MCP server is one more tool source, nothing outside tools/mcp/ knows the protocol exists, a session starts no server until one of its tools is called, and a turn never opens a browser — edgar mcp login NAME does, because a human ran it.

One detail that belongs to Core rather than to M8: whatever a server claims about its own tools (readOnlyHint and friends) is shown by edgar mcp list and never read by decide(). An MCP tool is always untrusted_output, and its category is shell for a local program, network for a URL.

28Subagents, routing rules and fallback

tools/builtin/task.py agents/spawn.py tools/execute.py

Look for: TaskTool spawn narrow_mode SpawnLimits execute_many

M9 has a tour of its own: Subagents, four stops on what an agent file is, how spawn() narrows, how consecutive task calls fan out, and why routing, escalation and fallback stay three things. What to carry from here: a subagent is not a second engine (ADR-0006). spawn() builds a second Runtime and calls the very same run_turn from stop 1, with a fresh Session, a narrowed policy and a slice of the parent's remaining budget. Its permission prompts share the parent's guard, so they share the same asking lock and carry the agent's name. edgar agents list|validate is cut from 1.0 (ADR-0053), not planned work still owed. Roadmap: M9

29Extensions, hooks, plugins, embedding

extensions/discovery.py extensions/hooks.py skills/activate.py __init__.py

Look for: discover Hook veto matching verify_command run

M10 has a tour of its own: Extensions, five stops on the manifest, hooks that veto, provider plugins, skill activation and edgar.run(). What to carry from here: an extension is a folder of files, a hook can observe or veto but never allow (EXT-4..7), and Python is a plugin surface only for providers, retrievers and sandboxes (ADR-0018). These are the formats 1.0 freezes. edgar ext list is the whole CLI surface 1.0 ships for them — ext validate and ext add moved to v2 (ADR-0053).

One piece belongs here rather than on that page, because it closes Core's verify gate (stop 12): deterministic skill activation [SKL-17] means the model never has to call the skill tool for a keyword the user typed or a path the last round touched. matching() finds those skills, bodies() loads them into the turn's attached context, and the same matches feed VER-1's precedence chain — verify_command() chains a loaded skill's own verify: command when nothing higher ranked (--verify, then an agent's frontmatter) claims the turn. Roadmap: M10

30Init and doctor

edgar init and /init [CFG-4] scaffold a project's AGENTS.md, a .gitignore fragment for .edgar/'s generated state, and a working, commented config.toml — from three plain files under templates/, not Python, so they cost nothing against the LOC budget the same way prompts/*.md already does not. Every write checks existence first and leaves the file alone if it is already there (ADR-0034's rule, extended here); init.run() is shared code, called both from the CLI and from cli/repl.py's "nothing configured" startup path, so a fresh checkout gets scaffolding, not just a model picker. edgar doctor [CFG-5] checks each provider's credentials (reusing cli/models.py's describe()) and connectivity, and warns when a directory sits inside iCloud Drive, OneDrive, Dropbox or Google Drive — a plain substring match on the resolved path, which cannot catch macOS's silent Desktop & Documents sync; that gap is named in a comment rather than hidden. 31Learning foundations

M12 · planned learning/learner.py learning/error_facts.py learning/experience.py

Learning from what you type and from what breaks. Nothing on this path reads tool output, error text or fetched content, and that is enforced by what each function accepts, not by filtering. Roadmap: M12

32The controller

M13 · planned controller/triggers.py controller/proposals.py controller/apply.py

Self-management that cannot hurt you. The triggers are pure checks, actions come from a whitelist of eight, and every change is dry-run by default, logged and revertible. The controller can only tighten policy. Roadmap: M13

33Skill synthesis

M14 · planned learning/synthesis.py learning/curator.py

Only verified procedures become skills. The synthesiser sees the outline of a run, never tool output. It writes only into .edgar/skills/learned/, and only after a passing check. Roadmap: M14

34Escalation

M15 · planned providers/escalation.py

A weak model that fails gets help from a stronger one, visibly: upward only, capped and announced. Compare it with routing (stop 14) and fallback (stop 22). Keeping the three apart is the point. Roadmap: M15

35The capability broker

M17 · planned broker/authorize.py broker/ticket.py broker/receipt.py

Every tool call answers to what the human actually asked for. A typed request becomes a ticket with caveats. A subagent can only narrow it. A pure authorize() vetoes calls in the pre_tool stage, and every decision goes into a signed receipt. Roadmap: M17

36Scheduling

M16 · planned schedule/due.py schedule/tick.py schedule/install.py

Unattended runs that cannot run away. Working out what is due is a pure function tested with a frozen clock. A run the harness schedules for itself never holds more authority than the run that created it. Roadmap: M16
