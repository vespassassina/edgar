A Tour of the Harness

A guided read of edgar: which files to open, in which order, and what to look for in each.

The agent harness you can read in an afternoon. Any model. No hidden calls. Nothing is done until it's verified.

Every stop links to the file on GitHub and names the functions worth finding. The order follows dependencies, not the alphabet: each stop only needs the stops before it. Keep the code open beside this page. The numbered steps in the diagrams match the numbered comments in the code.

The tour comes in three parts, one per tier, so you can read it a tier at a time. Core is built: read it now. v1 and v2 are planned. Their stops name the files they will be, the milestone that brings each one, and the seam in Core where it will attach. As each milestone lands, its stop gets links like the rest.

The promise is that Core can be read in an afternoon, so time yourself. If it takes longer, that is worth knowing: open an issue and say where you got stuck.

I. Core Built, M0 to M5

The smallest honest harness: one loop, eight tools, five providers, permissions, verification, sessions. At most 5,000 lines of code.

Stage 1. The spine about 45 minutes

These four files are the whole system in miniature. Everything else is detail hanging off them.

1The loop

core/loop.py

Look for: run_turn _Turn _start _ask _run_tools _check Runtime

The file opens with the whole turn as pseudocode, and run_turn follows it step by step, numbered 1 to 10 in the comments. The diagram uses the same numbers. Each step with any detail is a helper one level down; no helper calls another, and nothing recurses.

flowchart TD
    start(["1. record the prompt"]) --> safe["3. safe point:
pause, /steer"]
    safe --> caps{"4. over a
cost cap?"}
    caps -->|yes| budget(["budget_exceeded"])
    caps -->|no| ask["5. ask the model
_ask"]
    ask --> calls{"6. tool
calls?"}
    calls -->|yes| run["run them in order
_run_tools"] --> safe
    calls -->|no| steer{"7. steer
pending?"}
    steer -->|yes| safe
    steer -->|no| acted{"8. changed
something?"}
    acted -->|"no, or no check"| done(["9. completed"])
    acted -->|yes| check["run the check
_check"]
    check -->|passed| done
    check -->|"failed, tries left"| safe
    check -->|"failed, none left"| failed(["verification_failed"])

There are four ways out: budget_exceeded, completed, verification_failed, and a cancel, which raises. On a cancel, seal() first gives every open tool call a result, so the transcript stays valid.

Take with you: the safe point (step 3) is the only place a pause or a /steer takes effect. The previous round always ended on a complete call-and-result pair, which is what keeps the transcript valid (stop 16).

2The vocabulary

core/message.py

Look for: Message TextBlock ToolUseBlock ToolResultBlock ErrorRecord ThinkingBlock

These are the shapes the model sees. The comment at the top shows a whole conversation written in these types. Everything is frozen: compaction builds new transcripts rather than editing old ones. A failed tool call is a ToolResultBlock with is_error set, never an exception.

3The output

core/events.py

Look for: EventBus Event TurnStarted ToolProposed PermissionResolved TurnFinished

These are the shapes the outside world sees. The loop and tools never print; they emit events, and the renderer, the status line, --events and the tests subscribe. Each event says in a comment who emits it, and the comment at the top lists a typical turn's events in order.

4Done means verified

core/verify.py

Look for: verify Check

This is the smallest important file in the repository. When the model stops after changing something, the declared check runs. If it fails, its output goes back to the model while attempts remain. Decide for yourself whether it is as strong as the README claims.

Before moving on: can you draw the turn from memory?

Stage 2. The hands about 45 minutes

How the loop touches the world: where "the model asked" turns into "the thing happened".

5The tool contract

tools/base.py

Look for: Tool ToolSchema ToolContext ToolResult

A tool is a schema plus an async run. The schema's category (read, write, shell, network) is what the permission engine reasons about.

6The pipeline

tools/execute.py

Look for: execute _validate _failed

Every call from every source takes this one path, so this is the single place where a check on every tool call can sit.

flowchart TD
    call["a tool call"] --> proposed[/"ToolProposed"/]
    proposed --> known{"tool exists?"}
    known -->|yes| shape{"arguments a
JSON object?"}
    shape -->|yes| valid{"match the
schema?"}
    valid -->|yes| guard[["guard.check
decide, ask if needed"]]
    guard -->|allow| runit["run, with a timeout"]
    runit --> spillit["spill big output to a blob"]
    spillit --> block["ToolResultBlock"]
    known -->|"no: not_found"| err["error result"]
    shape -->|"no: validation"| err
    valid -->|"no: validation"| err
    guard -->|"deny: permission_denied"| err
    err --> block
    block --> back(["back to the model"])

Nothing here raises into the loop. A timeout or a crashing tool also becomes an error result the model can recover from.

7The decision

permissions/policy.py

Look for: decide _decide _mode Policy Allow Deny Ask

One pure function: no I/O, and the first match wins.

When nobody is there to answer, decide turns an Ask into a Deny with needed_prompt set, and edgar -p exits 5. Taint is sticky: once a tool returns content from the network, auto mode asks before shell and network calls for the rest of the session.

8The asking

permissions/guard.py permissions/matcher.py

Look for: Guard subject CATASTROPHIC credential inside

The I/O half that keeps decide pure. Guard works out what a call touches, builds the Policy, asks you when the answer is Ask, and remembers your "always" answers. The matcher holds the list of commands that never run and the detection of credential paths.

9The tools that can hurt you

tools/builtin/fs.py tools/builtin/shell.py

Look for: Read Write Edit Grep Shell Fetch

Read fs.py first. Fetch is the tool whose output is marked untrusted, which is what taints a session.

10Your own tools

tools/custom.py

Look for: CommandTool HttpTool load

This turns a CLI or an API into a tool with config alone. A command tool is an argv template and never a shell string. An HTTP tool has its host fixed and takes secrets only from the environment.

Before moving on: where exactly is the boundary between "the model asked" and "the thing happened"?

12Four vendors, one adapter

providers/openai_compat.py providers/quirks.py

Look for: OpenAICompatible Quirks QUIRKS

OpenAI, Azure, OpenRouter, Ollama and any compatible server share one adapter. How they differ is a table of data, not branches in code. Check whether the table earns the claim.

13The one that needed its own adapter

providers/anthropic.py

Look for: Anthropic

Ask yourself why this one needed its own adapter, specifically. Follow how thinking blocks, their signatures and cache breakpoints travel.

14When the model gets it wrong

providers/repair.py providers/routing.py

Look for: text_call arguments select_model

Small local models fence their tool calls or write them as plain JSON; the repair recovers them deterministically and never invents a call. Routing in Core is a pure function that binds roles to models. It never picks a model you did not name.

Skip these on a first pass: pricing.py, registry.py, fake.py, http.py.

Stage 4. The memory about 30 minutes

15The prompt

context/builder.py prompts/system.md

Look for: build system_text pinned

Everything the model is told, in one short file, and the function that puts it in front of the transcript. Nothing above the cache breakpoint changes within a session, so there is no date or anything volatile in the prefix.

16Compaction

context/compact.py core/units.py

Look for: compact elide fold assert_pairing units

The hardest correctness problem in the repository: shrinking a transcript without ever separating a tool call from its result. units.py is the invariant; compact.py works only on whole units. The stages run cheapest first.

17Sessions on disk

storage/transcript.py core/session.py core/cancel.py

Look for: Log replay Session seal

A session is recorded as JSONL, append-only, never rewritten. Undo, compaction and cancel each append a record, and replaying the file rebuilds the exact view. Check that the append-only claim holds everywhere, including for a cancel and for /undo.

19Skills

M6 skills/discovery.py skills/loader.py tools/builtin/skill.py

Only the frontmatter of each skill is read at startup; the body loads when the model calls the skill tool. A skill is instructions, never code that runs. Roadmap: M6

By the end of Core you should be able to answer three questions without the docs open. What happens in a turn, step by step? Where does every tool call pass, and what can stop it there? How does a long session stay valid as it is compacted, cancelled and resumed? Any file you could not follow is a readability bug: open an issue.

20Memory and session search

M7 memory/store.py memory/facts.py memory/recall.py

Look for the security boundary: an active fact comes only from text a human typed or from an ErrorRecord the harness computed. Everything else, including the model's own remember calls, stays pending until you confirm it. The pinned set is frozen at session start so the prompt prefix stays stable. Roadmap: M7

21MCP

M8 tools/mcp/client.py tools/mcp/schema.py

MCP tools are one more tool source: they go through the same execute() as the built-ins (stop 6). Their results are untrusted, and decide() ignores whatever a server says about its own tools. Roadmap: M8

22Subagents, routing rules and fallback

M9 tools/builtin/task.py agents/spawn.py providers/fallback.py

A subagent is not a second engine. The task tool calls the same run_turn (stop 1) with a fresh transcript and a narrower policy. Consecutive task calls fan out concurrently. Fallback goes sideways when a provider is down, and is kept apart from routing and escalation. Roadmap: M9

23Extensions, hooks, plugins, embedding

M10 extensions/manifest.py extensions/hooks.py sandbox/base.py

An extension is a folder of files: tools, skills, agents and hooks. A hook can observe or veto, never allow. Its veto sits in the pipeline's pre_tool stage, just before the permission check, and a failing hook denies. Python is a plugin surface only for providers. Roadmap: M10

24Init and doctor

M11 config/init.py config/doctor.py

Scaffolding a project and checking an environment. Skim it: it is surface, like stage 5. Roadmap: M11

III. v2 Planned, M12 to M17

It learns, and runs unattended: learning, the controller, escalation, the capability broker and scheduling. At most 11,000 lines of code in all. v2 is removable. Nothing in Core or v1 imports it, and CI deletes the v2 packages and runs the v1 suite to prove it.

25Learning foundations

M12 learning/learner.py learning/error_facts.py learning/experience.py

Learning from what you type and from what breaks. Nothing on this path reads tool output, error text or fetched content, and that is enforced by what each function accepts, not by filtering. Roadmap: M12

26The controller

M13 controller/triggers.py controller/proposals.py controller/apply.py

Self-management that cannot hurt you. The triggers are pure checks, actions come from a whitelist of eight, and every change is dry-run by default, logged and revertible. The controller can only tighten policy. Roadmap: M13

27Skill synthesis

M14 learning/synthesis.py learning/curator.py

Only verified procedures become skills. The synthesiser sees the outline of a run, never tool output. It writes only into .edgar/skills/learned/, and only after a passing check. Roadmap: M14

28Escalation

M15 providers/escalation.py

A weak model that fails gets help from a stronger one, visibly: upward only, capped and announced. Compare it with routing (stop 14) and fallback (stop 22). Keeping the three apart is the point. Roadmap: M15

29The capability broker

M17 broker/authorize.py broker/ticket.py broker/receipt.py

Every tool call answers to what the human actually asked for. A typed request becomes a ticket with caveats. A subagent can only narrow it. A pure authorize() vetoes calls in the pre_tool stage, and every decision goes into a signed receipt. Roadmap: M17

30Scheduling

M16 schedule/due.py schedule/tick.py schedule/install.py

Unattended runs that cannot run away. Working out what is due is a pure function tested with a frozen clock. A run the harness schedules for itself never holds more authority than the run that created it. Roadmap: M16

Keeping this tour honest. The tour changes in the same commit as the code it describes. tests/unit/test_tour.py fails when a linked file no longer exists, when a name under "Look for" is gone from its files, when a size in the table drifts more than 100 lines of code from the real one, when a package has no row, or when a planned file lands and its stop still says planned. It cannot tell when a description has gone stale, so reread a stop whenever you change its code. The source of this page is docs/tour/index.html.
