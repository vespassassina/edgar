Built M13
Kept in sync by a test

An agent that can adjust its own settings is the feature everyone wants and the one nobody can make safe. The reason is not subtle: the component deciding what to change is a language model, the thing it is changing is the sandbox that language model runs in, and the text it is reasoning over came out of a session that may already have gone wrong. Give it a free hand and you have built a machine that argues itself out of its own restraints.

So the whole of controller/ is arranged around removing the free hand. Whether a call happens at all is decided by arithmetic, not by a model. What the model may ask for is a closed list of eight, checked by a parser, not by a prompt. Policy changes go one direction only, through a pure function a generated test hammers. And everything that persists is dry-run by default, logged, and revertible by id.

Stage 1. Deciding without a model about 10 minutes

1Five numbers and a threshold each

controller/triggers.py

Look for: Signals CHECKS tripped summary

The first decision in this milestone is the one that costs nothing and is easiest to get wrong: who decides whether to call the controller. If the answer is "a model", then every turn pays for a call whose only job is to say "no call needed", and the harness has acquired exactly the hidden cost its positioning says it does not have.

So the answer is arithmetic. Signals holds five numbers about the turn that just ended — how full the context got, how many turns in a row ended with a failing tool call, how much of today's cost cap is gone, how much the model wrote, how long it took. CHECKS is a table of five one-line comparisons against the thresholds in [controller], and tripped() returns the names that fired. Nothing here does I/O, holds state, or knows what a provider is, which is the same shape as permissions.decide() and routing.select_model() and for the same reason.

Two details in the table are worth stopping on. A threshold of zero for error_streak turns that check off rather than firing it on every turn, which is the reading a person setting a config value to zero actually means. And burn_rate is computed by the caller as today's spend over the daily cap, so a project with no cap has a rate of zero and never trips it: there is no sensible fraction of a limit that does not exist.

summary() exists because a name is not enough. "errors" does not tell the controller whether two things failed or twenty, and the number is most of the signal. The line it builds is both what goes into the outline the controller reads and what edgar controller log prints back to you, which keeps the two from drifting apart.

Take with you: before you let a model decide something, check whether a comparison would do. The comparison is cheaper, it is testable, and you can read it.

Stage 2. The whitelist about 15 minutes

2Eight actions, and no ninth

controller/proposals.py

Look for: ACTIONS Proposal parse BUILDERS targets Outline Rejected

The controller answers with one JSON object and this file turns it into one of eight frozen types, or into a Rejected saying why it could not. The shape is deliberately the same as permissions/policy.py's Allow | Deny | Ask: a tagged union of small dataclasses, matched with isinstance by whoever acts on it. A union is a whitelist that the type checker enforces, which is a better place for it than a prompt.

Read parse() as three steps, and notice that step two is the entire security property. An action name that is not in ACTIONS never reaches a builder, so a model that invents run_shell or disable_checks gets a logged rejection rather than a surprise. The eight are compact, switch_model, tighten_policy, warn_user, abort, propose_instruction, propose_skill and noop.

There is deliberately no learn action, and ADR-0017 is why. That document closed four roads by which text the harness did not choose could become an active fact; a controller that could write one would be the fifth, and the widest, because it reads a summary of a session that may already be compromised. warn_user can suggest that you type /remember. A human types it.

targets() is ROUTE-8 in five lines and is worth contrasting with the obvious alternative. A switch_model proposal could be checked at apply time against whatever the provider registry happens to accept; instead the target set is computed here from what the project already named — every [[route]] rule's model, plus each role's binding in [model] — and a string outside it never becomes a proposal at all. A model that asks for a host you never configured is refused by the parser, not trusted and then audited (PRV-15).

The two rejections worth trying yourself are in tests/unit/test_controller_proposals.py: a tighten_policy that says allow, and a switch_model naming a plausible model that this project does not use. Both are fabricated by hand. No test in M13 calls a model.

Last, Outline, which is what the controller is given. It is counts and names: which checks tripped, which tools ran, how many calls failed, what the declared check said, which models are switchable. No tool output, no error text, no prompt body. That is the same discipline the learner works under (Learning, stop 1) for the same reason — the controller's answer changes how edgar behaves, so what it reads has to be text edgar wrote about itself.

Take with you: a whitelist enforced by a parser is worth more than the same whitelist written in a system prompt, because one of them is a rule and the other is a request.

Stage 3. One direction only about 15 minutes

3Humans widen, machines tighten

controller/tighten.py

Look for: Narrowing narrow is_narrowing MODES VERDICTS Malformed

This is the file the whole milestone leans on. "No automated component may widen policy" is one of edgar's standing constraints (PERM-8, ADR-0021), and narrow() is the controller's half of it: a pure function over the current Policy and a proposed Narrowing, returning either a stricter policy or one line naming the field that tried to loosen.

Four fields may move, and each has its own meaning for "stricter". mode travels one road only, yolo → auto → ask → read-only, never back. shell_deny is added to and never taken from. write_paths may shrink, and only to patterns already in the list. Per-tool verdicts may go allow → ask → deny and never the other way.

Two of those rules are blunter than they look, on purpose. A narrowing may not introduce a new write_paths pattern even when it plainly looks tighter, because deciding that ./src/** is narrower than ./** is a judgement about glob semantics that this function cannot make and a model should not be trusted to make. And an explicit allow is refused outright rather than compared, because an explicit rule overrides the mode's own default in permissions/policy.py — so it can widen even where it looks like a no-op.

Notice where each check lives. allow, and a mode that is not a mode, are refused in Narrowing.from_dict, at parse time, because neither answer depends on the current policy. Whether ask is looser than what you already have does depend on it, so that check is in narrow(). Both were found by the property test rather than by reading: the first draft parsed {"rules": {"shell": "allow"}} into a perfectly valid proposal and left the refusal to apply time.

Then the last four lines of narrow(), which look redundant and are the point. It rebuilds the policy and asks is_narrowing() whether the answer it just produced is actually stricter than what it started from. The field-by-field rules above are where a mistake would live; this is a second, simpler statement of the same property, written once and used both here and as what tests/property/test_controller_tightening.py asserts. A bug has to defeat both.

That property test is the reason this function is shaped the way it is. It generates policies and narrowings together — looser modes, unknown verdicts, patterns the policy never had — and asserts on every pair that what comes back is at least as strict, or is a refusal. It also asserts the quieter half: an accepted narrowing was actually applied, so a narrow() that gave up and returned the original policy would fail. A function that returns its input is a narrowing too, and it is the wrong one.

Take with you: when a rule has a direction, write the direction down as an ordered tuple and index into it. MODES.index(a) < MODES.index(b) is a sentence you can check; four nested conditionals about which mode is stricter is a sentence you can only hope about.

Stage 4. The log is the state about 10 minutes

4Dry run, one row, and a revert by id

controller/store.py, controller/apply.py

Look for: Controls Mutation overrides apply Site Outcome revert approve PERSISTED

Read overrides() before anything else on this stop, because the design is in that one query. There is no table of current settings. What edgar is running under is derived from the log: the newest applied row per action wins. So reverting is a single UPDATE on a single row, the log and the live state can never disagree, and there is no second place to look when they seem to (CTRL-10). Compare memory/store.py's undo, which reached the same shape from the other direction.

apply() is eight branches with no table, which is the opposite of proposals.py two stops ago and worth the inconsistency: a dict keyed on the class would hand every handler a bare Proposal and need a cast in all eight to get the real type back. Where the type checker can do the work, let it.

The eight split three ways, and the split is the whole safety argument. compact and switch_model outlive the session, so they are dry-run by default: the row says what would have changed, and edgar controller apply ID is a person turning it into what did (CTRL-6). tighten_policy, abort, warn_user and noop act now and die with the process. And the two propose_* actions write a file and stop — they are never "applied", in any mode.

tighten_policy not being dry-run is a decision you could make differently, so it is worth the sentence. CTRL-8 guarantees the change can only make the session stricter; a tightening that waits for approval is a tightening that does not happen while the thing it was reacting to is still going on. It is logged like everything else, and it ends with the session either way.

Then abort, which is the one that sounds like it should do more than it does. The gate runs after a turn, so there is no turn left to stop. What abort does instead is take the session's hands away: narrow() to read-only for the rest of it, in memory, never persisted. That is not a consolation prize. The failure it exists for — a model looping, repeating the same edit, burning the budget — is a failure that continues into the next turn, and read-only is exactly the thing that stops it.

Last, the rule this file is shaped around: nothing here can write a hand-authored file. propose_instruction writes Markdown into .edgar/proposals/, named after its own log row, saying what to add; a person adds it. Notice what the code does not contain — the name of the file the instructions live in. edgar genuinely does not know whether that is AGENTS.md, a CLAUDE.md or a prompt profile, and a path this code never spells is a path it can never open. That is also what tests/unit/test_controller_boundary.py checks, by reading every string literal in the package out of its syntax tree (CTRL-12, ADR-0008).

Take with you: if you can derive the current state from the audit log, do, and delete the copy. Two sources of truth about what a system is doing is one more than anybody can keep correct.

5One call, in the background, that cannot fail your turn

controller/gate.py, controller/__init__.py

Look for: Gate BRIEF attach overrides _running _look

Everything so far has been pure or local. This is the file that watches a real session: it subscribes to one bus, counts failures off ToolFinished, starts a clock on TurnStarted, and when TurnFinished arrives builds the five Signals and asks tripped(). On an ordinary turn that is the end of it — no call, no cost, no latency (CTRL-2).

Look at the call itself, and at what it is handed: provider.stream(prompt, [], …). The second argument is the tool list, and it is empty. ADR-0008 asked for a "hard-limited tool set"; the only limit that needs no maintenance is zero. The controller cannot read a file, run a command or call anything at all: its entire power is the shape of its answer, and that answer is one of eight (CTRL-3). The prompt it gets is an Outline — which checks tripped, which tools ran, how many calls failed, what the declared check said. Counts and names. The same discipline the learner works under, for the same reason (MEM-9).

The bus is synchronous; a model call is not. So the gate does what extensions/hooks.py already does with a fired hook: asyncio.ensure_future, and a module-level _running set so the task is not collected mid-flight. _ended() returns immediately, and nothing below that line can reach the turn. A -p run that exits at once may drop a call still in flight, and that is CTRL-11 working as written rather than a bug: whatever the controller was about to say, the turn does not wait for it.

_look() holds the only bare except in the package, on purpose. A housekeeping mechanism that can break your session is worse than no housekeeping at all, so a controller that times out, or answers nonsense, or cannot reach its host, leaves a row in the rejected table and nothing else.

Then __init__.py, which is two functions and the whole seam. attach() subscribes the gate; overrides() reads the log. cli/setup.py reaches both by name with importlib, exactly as it reaches edgar.learning, so no Core, v1 or v2 module imports this package and deleting the folder costs one quiet ModuleNotFoundError (NFR-12, ADR-0015). Note the first line of attach(): with [controller] enabled false, which is the default, it subscribes nothing and returns. A harness whose promise is "no hidden calls" does not start making one a turn because you upgraded.

Take with you: the cheapest way to make an automated helper safe is to give it nothing to work with. No tools, one answer shape, and a wrapper that swallows its failures.

6Three commands, and the one that is missing

controller/cli.py

Look for: command USAGE

edgar controller log prints what it did, what it would have done and what it was refused, newest first, with the id in the first column because the id is what the other two commands take. edgar controller apply ID turns one dry run into the real thing; edgar controller revert ID takes one applied row back out. That is the entire surface.

The refusals are printed under the mutations rather than hidden behind a flag, and that is the deliberate part. A controller that gets refused every single turn is a configuration problem — a threshold set too low, a model that cannot follow the brief — and the failure mode worth designing against is the one where nothing says so.

Now the missing command. There is no edgar controller run. You cannot ask for a controller call from the outside, because the gate is the only thing that starts one and a crossed threshold is the only thing that asks the gate (CTRL-2). Adding a manual trigger would be one line and would quietly undo the argument the rest of this page makes.

The file lives here rather than in cli/, like learning/cli.py before it, and for the same reason: a module under cli/ that imported edgar.controller would break tier isolation and fail tests/unit/test_architecture.py. cli/main.py reaches it by name, so deleting the package deletes the commands and nothing else (NFR-12).

Take with you: the commands you leave out are part of the design. Ask what each new verb lets someone bypass.
