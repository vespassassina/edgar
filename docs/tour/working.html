Everything on this page is about the difference between what a session remembers and what it is working on. Memory is slow, confirmed and shared between sessions. Working state is fast, unconfirmed and thrown away at the end: the file you just attached, the plan you agreed on, the list of things still to do. The design problem is that working state has to survive compaction without becoming memory, and without breaking the pairing invariant that compaction protects (ADR-0025).

Stage 1. What you bring in about 10 minutes

1@path

context/attach.py

Look for: TOKEN ACCEPTS Attached attach

Fifty lines, and almost all of the thinking is in what they refuse. A word beginning with @ in a typed line is a file to attach; the line itself is never rewritten, which is the point. What the human typed stays exactly as typed, because that string is the one thing allowed to create an active fact (MEM-9), and the file's text leaves this module as a separate body that can only ever become a TextBlock(attached=True). The boundary is a type, not a filter.

Read _refuse before attach. A missing path, a directory, a credential file, a path outside the working directory and anything that is not text each get a sentence naming the path and saying what @path accepts, and the turn does not run. None of them raises. Notice which case is not there: .edgar/config.toml attaches like any other file, because the permission engine asks about a control file only when a tool would write it. Adding a rule here that the engine does not have would be this module inventing policy of its own, which is exactly what edgar tries never to do.

The last line of attach is a reuse worth noticing: an oversized attachment goes through the same spill as oversized tool output, so it keeps its head and tail and leaves a blob path the model can read. One mechanism, two callers.

Take with you: a feature that only adds context is still a security boundary. The interesting code is the refusals.

2The pinned block

context/working.py

Look for: Working render place enter leave

Working state is the plan and the todo list: fast, unconfirmed, gone at the end of the session. Memory is the opposite of all three, which is why they are different things in different files. The whole design is in where Working lives: on the Session, never in session.transcript. Compaction only ever rebuilds the transcript, so it cannot reach this, and the pairing invariant (CTX-4) holds here by construction rather than by care. There was a version of this that put a pinned message in the transcript and taught every stage to step over it. Every stage is where bugs of that kind live.

render makes one message; place puts it just above the current turn, below the cache breakpoint because it changes. It is the same bytes in every request until the state itself changes, which is what makes a sixty-turn session with a dozen compactions send an identical list every time.

Then read enter and leave, which are plan mode entire. enter sets the session's existing mode to read-only and remembers what it was; leave puts that back. There is no second permission engine and no plan-mode branch in decide(): a write in plan mode is denied by the ordinary read-only rules. And because leave can only restore a mode the session already had, and only a typed /go calls it, nothing automated can widen policy through this file (invariant 2).

Take with you: the cheapest way to survive a transformation is to live outside what it transforms.

Stage 2. What the model is working on about 20 minutes

3The todo tool

tools/builtin/todo.py

Look for: ITEM TodoTool run

Forty lines, one call, no verbs. There is no add, no complete, no reorder: the model sends the whole list as it should read now, and that replaces what was there. A diff against a list the model cannot see is how todo tools drift out of step with the conversation; a whole list cannot drift.

Two details are worth a minute. The tool's category is read, because it touches no file the user owns: that keeps it out of the verify gate, and keeps it callable in plan mode, where writing the list is the work. And the update leaves by the event bus as TodoUpdated, which the status bar draws and the session log records, so --resume brings the list back with no separate save path. The event is the record.

Take with you: a tool with one verb has no state machine to get wrong.

4Looking at it

cli/inspect.py

Look for: rows BREAKPOINT context_show route_explain agents_command

edgar context show prints the prompt a session would send: one row per section, with its token count, and the cache breakpoint drawn where it falls. It calls no provider. It does not re-implement the assembly either, which is the part worth copying: it calls the same build and system_text a turn calls, so a command that lied about the prompt would have to lie by assembling a different one.

The counting has a small honest trick in it. The prefix's sections are joined into one system message, so a section's count is the difference between two running totals of that same join. The rows therefore add up to the message, and the message adds up to the prompt, whatever the separator between sections happens to be. The test asserts exactly that: the printed rows sum to the builder's own total.

The other two commands are the same idea pointed elsewhere. edgar sessions compact ID calls the loop's own compact(force=True) against a session replayed from disk, and because compact() appends one line per stage to that record, the history is added to rather than rewritten and --resume replays into the compacted view. edgar config show --resolved prints every effective key beside the layer it came from, with a credential shown as ***: a key is never in the config in the first place, only the name of the variable holding it.

M22 added two more of the same shape. edgar route explain [PROMPT] calls routing.select_model() — the pure function a turn calls — once per role and prints its Selection.reason, then walks the rules saying matched or skipped and why. It contacts nothing and needs no key. It also declines to flatter itself: the main turn passes a bare RoutingContext(), so a rule keyed on mode, tags or schedule can never match for the main role, and the command shows that instead of inventing a richer context no turn would ever build. edgar agents list|validate runs agents/discovery.py's own walk, folding an extension's agents in only when the project is trusted, exactly as a session does; validate reports each problem with the line the offending key sits on, so the fix is one jump away.

Take with you: an inspection command should read the code it inspects, never a second copy of it.

Before you go: you attach a file that tells the model to remember something about you. Which of edgar's boundaries stops that from becoming a fact, and where in the code is it enforced?
