The rule that keeps them small: extensions are files; Python is a plugin surface for providers, retrievers and sandboxes only (ADR-0018).

Stage 1. A folder of files about 12 minutes

1The manifest

extensions/manifest.py extensions/discovery.py

Look for: Manifest read _NAME Found discover _one disabled_from_config

An extension is a directory with an edgar.toml in it and the rest is ordinary files. Manifest is forty lines because it is a description, not a program: a name, a version, and lists of what the folder contributes. _NAME is the character rule, and it is strict on purpose — a name becomes part of a tool name, which the model sees and a permission rule may match.

discover is the same layering as skills and agents: built in, then user, then project, with the later one winning by name and every find remembering its path. Found carrying that path is what lets an error say which of two files called git it means.

disabled_from_config is the half worth dwelling on. Turning an extension off is a config edit a human makes; nothing in the running system can enable one. That is the same rule as permissions, applied to code loading.

2Hooks that veto

extensions/hooks.py

Look for: EVENTS Hook from_config from_extension _matches _run veto listener _fire

A hook is a command line attached to a named event. Read EVENTS first: the list is short and closed, so there is no way to attach to an internal detail that might move. _matches is the filter — a hook usually cares about one tool, or one path pattern — and it runs before the command is spawned, so the common case costs nothing.

The important asymmetry is in veto: a hook may refuse, and it may observe, and it can never approve something the permission engine denied (ADR-0021). A veto is not an exception either — it becomes an error tool result with a reason, and goes back to the model like any other tool failure, so the model can adapt instead of the run dying.

_run is where the care is: a timeout, a captured output cap, no shell, and a hook that crashes or times out is treated as a hook that said nothing rather than one that said no. Decide for yourself whether that default is the right one; it is a real trade-off and the comment says so.

Take with you: listener and _fire keep observe-only hooks off the critical path. Only vetoing events are waited for.

Stage 2. The Python surfaces about 10 minutes

3Provider plugins

providers/registry.py

Look for: BUILTIN KINDS split resolve _plugin

Eighty lines that do three things. split parses provider:model. resolve maps a name to an adapter through BUILTIN, importing the module only at that moment — no edgar.providers.* at startup, which is invariant 3 (ADR-0012). _plugin is the third-party door: an entry point group, looked in only after the built-ins, and a failure there names the distribution that registered the broken adapter rather than raising somewhere in the loop.

This is one of the six ports (ADR-0022). The test worth reading alongside it is the one asserting the core imports no adapter: the seam is enforced, not merely intended.

4Skill activation

skills/discovery.py skills/activate.py

Look for: Skill lint matching activate bodies

A skill is a markdown file, or a folder with a SKILL.md and whatever else it needs (ADR-0041). Only the name and description of each skill sit in the prompt; the body is read when the model calls the skill tool. That is the same deferral as MCP's deferred schemas, and for the same reason.

matching is the cheap pre-filter and activate the actual load; bodies is what gets handed back. lint is the one that will save someone an afternoon: it is what edgar doctor uses to say a skill's front matter is wrong, in the file, before a session ever sees it. This module is a port too — a skill source, per ADR-0022 — which is why discovery and activation are separable at all.

5edgar.run()

edgar/__init__.py

Look for: run __version__

The embedding API is one function, and its shape is the argument. It takes a prompt and returns a result; everything else — config, provider, tools, permissions — comes from the same layered resolution a CLI run uses, so a program embedding edgar cannot accidentally get a different harness than the one its user configured.

Two details. The imports are inside the function, because import edgar must stay as cheap as import edgar.cli.main. And there is no callback parameter: streaming and progress come off the event bus, which is the same decision as everywhere else (ADR-0011). __version__ lives here and is bumped together with pyproject.toml at release.

6The gate before a copy

skills/audit.py extensions/validate.py

Look for: DANGERS audit render diff validate _agreed

Extensions are copied in from a path, never installed from an index, so the copy is the only moment anyone checks what is arriving (ADR-0042). audit answers two separate questions and keeps them apart: conformance (does it load, does the description say when to use it, do its paths stay inside the folder) and dangers (a download piped into a shell, sudo, a recursive delete, text telling a session not to ask or not to tell, hidden characters, hosts, credential locations, and every bundled script with the programs it calls). DANGERS is a table, one row per rule, so a new pattern is a row and a test rather than a branch. No model is asked anything: the text under review may be hostile, and a verdict a model decides is a verdict an injection can argue with.

diff prints the fixes it would make and never applies them, so the audit writes nothing. In validate.py, _agreed is the "humans widen, machines tighten" line in one function: a clean audit asks [Y/n], a danger finding asks [y/N], and with no terminal a danger finding is refused unless a human passed --yes. The copy itself goes to a staging folder and then one rename, so a session sees the whole extension or none of it — never half of one.

Before you go: an extension ships a hook on pre_tool and an agent that uses a tool the extension also ships. Trace the order in which those two are discovered, and name the point at which a permission decision is made.
