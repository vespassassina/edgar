Stage 1. Re-entering the loop about 15 minutes

1What an agent is

tools/builtin/task.py agents/definition.py agents/discovery.py

Look for: TaskTool subject AgentDefinition Found scan _agent

task.py is about fifty lines and that is the point. It validates, looks the agent up, hands the work to spawn, and returns one string. subject is the short label the status bar shows, so a human watching four rows scroll past knows which one is which.

definition.py is smaller still: an agent is a markdown file with front matter — a name, a description, which tools it may use, optionally a model. Nothing executable, nothing Python, which is the extension model's rule (ADR-0018). discovery.py is the usual layered search, project over user, first definition of a name winning, and Found carries where each one came from so edgar doctor and error messages can say which file they mean.

Look at what a subagent does not inherit: the parent's transcript. It gets a prompt and a fresh session. That is the whole reason to use one — the parent's context stays small — and it is also why a subagent cannot ask the parent a question.

2Narrowing, not widening

agents/spawn.py

Look for: spawn SpawnLimits HARD_DEPTH subagents_config narrow_mode _cap _subset

This file is where the second invariant lives: humans widen, machines tighten (ADR-0021). Read narrow_mode and _subset together and satisfy yourself that there is no path by which a child ends up with a permission mode or a tool its parent did not have. An agent file asking for a tool the parent lacks gets the intersection, silently and deliberately.

HARD_DEPTH is a constant, not a setting: a subagent may spawn, but the nesting stops at a depth the config cannot raise. _cap divides the parent's remaining budget rather than granting a fresh one, so ten subagents cannot cost ten times the cap. SpawnLimits holds the rest — concurrency, depth, per-child ceilings — in one dataclass so the rules are readable in one place.

Take with you: every limit here is checked at the moment of spawning, where a clear error is possible, rather than mid-turn where it would only produce a confusing failure.

Stage 2. Several at once about 10 minutes

3Fan-out, and watching it happen

tools/execute.py cli/statusbar.py

Look for: execute execute_many _fan_out_group FRAMES Status StderrLine rows terminal_ready

Tool calls from one response run in order — that is Core's rule and it has not changed. execute_many adds exactly one exception: a consecutive run of task calls goes concurrently [TOOL-12]. Find _fan_out_group and check the two properties that matter: an ordinary tool between two task calls breaks the group, and the results still come back in call order however they finished. A subagent that fails becomes an error result for that call and does not cancel its siblings.

statusbar.py earns its size on the terminal, not on the logic. It subscribes to the event bus like every other output component (ADR-0011) and draws one row per running agent [SUB-9]. The details to look for are the defensive ones: terminal_ready refuses to draw when stderr is not a terminal, so piped and scheduled runs produce clean output, and StderrLine exists so that anything else printing to stderr does not end up interleaved through a half-drawn frame.

Stage 3. Choosing a model about 10 minutes

4Three mechanisms, kept apart

providers/routing.py providers/fallback.py

Look for: Role RoutingContext Route Selection select_model check_capabilities routes_from_config Candidate NoFallback choose next_provider chain_from_config

Routing, escalation and fallback get conflated everywhere else. Here they are three files and one of them is not built yet (ADR-0013). Routing decides up front: select_model is a pure function from a RoutingContext and a list of Route rules to a Selection, which is why it is property-tested rather than mocked. Fallback goes sideways when a provider is unreachable and never reduces capabilities — choose skips a candidate that cannot do what the selected model could. Escalation goes upward on capability failure, and it is v3; there is no file for it yet.

check_capabilities is where a model with no tool support is refused, and the place matters: at selection, with a message naming the model and the rule that chose it, rather than as a provider error halfway through a turn [ROUTE-6]. NoFallback is the honest ending — when the chain is exhausted the run stops and says so, instead of quietly reaching for something the user never configured (ADR-0023).

Before you go: the model emits three task calls and a read call between the second and the third. How many run concurrently, in what order do the results land, and what would change if the read came last?
