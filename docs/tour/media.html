This milestone is two halves that look unrelated and are not. Images are the expensive half: one new content block, touched by serialisation, token counting, compaction and two CLIs, and every one of those had to be taught something. Web search and git are the cheap half: both arrived as files in examples/, with zero lines added to src/. The milestone is worth an hour mostly because the contrast is the whole argument for the extension formats (ADR-0052, ADR-0060).

Stage 1. The picture itself about 25 minutes

1One new block

core/message.py

Look for: ImageBlock images

Four fields: ref, media_type, width, height. Frozen and slotted like every other block, and deliberately nothing else. The test for whether a field belongs here was narrow on purpose — does serialisation or token counting read it? ref and media_type are what an adapter needs to build a request; width and height are what image_tokens needs to price it. A filename, a caption, a checksum, a source URL all had plausible cases and none of them had a caller, so none of them is here. This file is the frozen vocabulary the whole harness shares: a field added on spec has to be carried by every adapter, every test and every stored session forever, and taking one away later is a migration.

Notice what is not a field: the bytes. An ImageBlock is a reference to a file under sessions/<id>/blobs/. The JSONL record of a session therefore never contains base64, which keeps a transcript greppable and keeps a session with twenty screenshots in it a small file.

The second half of the change is Message.images, a convenience that reaches into both a message's own blocks and its tool results. Everything downstream — counting, eliding, serialising — reads that one property instead of walking blocks itself.

Take with you: in a vocabulary everything depends on, the fields you leave out are the design.

2Where the bytes go

tools/spill.py

Look for: spill spill_image SIGNATURES

Read spill first, which M5 wrote for oversized tool output: it writes a file under the session's blobs and hands back a path. spill_image sits beside it and shares the writing, not the policy. The distinction is the one judgement worth arguing about on this page. Text spills conditionally, when it is too big, and keeps a head and a tail so the model still sees something. An image spills always, whole, because half a PNG is not a smaller PNG. Two different rules with one line of shared file-writing between them: making the existing function take a flag would have put both rules in one body, and the flag would have had to reach every existing caller.

Then read SIGNATURES, which is how a file becomes a picture. There is no image library in edgar and no new dependency: PNG, JPEG, GIF and WebP each announce themselves in their first bytes, and each carries its dimensions a fixed distance in. Fifteen lines of header reading against a dependency that would have doubled the install size. A file whose header cannot be read is still an image; it just has width and height of zero, which stop 5 has to price.

Take with you: "reuse it" and "extract the shared part" are different answers. Share the mechanism, not the policy.

3The model that cannot see

providers/quirks.py · providers/routing.py

Look for: images check_images check_capabilities

images is one more column in a table that already had several. That is the whole point of quirks-as-data: a capability is a row, never a branch in the loop. Read the table and you can say which model sees, without reading any code.

check_images is deliberately built to the shape of check_capabilities, which M9 wrote for ROUTE-6, and it refuses in the same place: where the model is chosen, before a request is built and before a cent is spent. The alternative — send it and let the provider 400 — costs a round trip and produces an error in the provider's words rather than edgar's. Follow its caller into cli/oneshot.py and cli/repl.py and notice it fires on the attachment, not on the turn.

There is a second path for the same problem, because there are two ways an image arrives. An attachment is refused up front; a picture a tool produces mid-turn cannot be, since the model is already chosen. So ToolContext carries an images flag, and read on a picture answers a blind model with a sentence saying what the file is and that it cannot look. That is not an error result: the call worked, and the model gets to decide what to do next.

Take with you: when a new capability needs a refusal, find the refusal the last one used and copy its shape and its timing.

4Three ways to say the same picture

providers/openai_compat.py · providers/anthropic.py · providers/fake.py

Look for: _parts _image encoded

This is where the bytes come back. encoded lives in providers/http.py because both real adapters need it and neither should own it: it reads the blob and base64s it, and raises a ProviderError when the file is gone rather than sending an empty image. The base64 exists for the length of one request and is never stored.

Then read the two shapes side by side. Chat Completions wants a content array with an image_url part holding a data: URL; Anthropic wants a block with a source table naming the media type and the data separately. Both adapters translate and neither decides anything — the same difference as every other line in these files.

The interesting case is a picture a tool produced. Anthropic can put an image directly inside a tool_result; the OpenAI shape cannot, so openai_compat follows the tool results with one extra user message carrying them. Different bytes on the wire, same conversation.

Finish on the fake provider, which is the leverage the whole suite runs on. It cannot look at anything, so it says what arrived: media type, dimensions and reference. That one line is what lets a test assert an image survived a turn and a --resume without any provider being reachable.

Take with you: a fake that reports what it received is worth more than a fake that pretends to understand it.

5What a picture costs

context/tokens.py

Look for: image_tokens _fit approx_message_tokens PIXELS_PER_TOKEN

Forty lines, no I/O, no clock, no config: pure arithmetic over four integers, which is the only reason a number this load-bearing can be trusted. Compaction decides when to run from it, and a budget that undercounts images silently sends requests that get rejected for length.

A picture costs by its geometry, never by its bytes. A 4 MB photograph and a 40 KB screenshot of the same size cost the same, because the model resizes before it ever looks. Two rules cover every provider edgar speaks to: Anthropic shrinks to a 1568-pixel longest side and charges area over 750, while the Chat Completions family shrinks to fit 2048, then the short side to 768, and charges a base plus one price per 512-pixel tile. _fit is the shrinking both share, and it never enlarges.

Read the first two lines of image_tokens. A header that could not be parsed left the size at zero, and rather than guessing at a picture nobody measured, it charges one tile's worth. Wrong, certainly, but wrong by a bounded amount in a known direction — which is what you want from an estimate that gates compaction.

Take with you: when the input might be unmeasurable, decide what you charge for "unknown" before you need it.

6Eliding an old picture

context/compact.py

Look for: elide _stub ELIDED

The most dangerous file in the milestone, because of invariant 1: every assistant message with tool calls is followed by exactly one tool message whose result ids match, and every provider returns 400 if you break it. Compaction holds that invariant by only ever removing, stubbing or summarising whole units, and by never trimming inside one.

So the change is inside _stub, the per-block helper elide already mapped over everything before the cut, rather than a second pass of its own. That was the judgement call. A separate _elide_images would have been easier to read in isolation and would have been a second function that knows where a turn may be cut — and the value of the invariant is that exactly one function knows that. An old picture becomes a line naming it: media type, dimensions, and the reference, so a human can attach it again and the model stops paying for it on every request. The bytes were never in the transcript anyway, only in the blobs, so nothing is lost that was not already on disk.

Two details make it safe. A tool result that carried images is stubbed with them — text and pictures replaced together, one unit elided whole, never a stub still dragging its screenshots along. And the operation is idempotent: an ImageBlock becomes a TextBlock that stays itself on a second pass, and an already-stubbed result returns early. The property suite runs elision twice over transcripts with an image on every other tool result and asserts the pairing survives both.

Take with you: when one function is the only thing that knows an invariant, the cost of extending it is almost always lower than the cost of a second function that also knows.

7Two ways in

context/attach.py · tools/builtin/fs.py

Look for: attach _refuse Read ToolFinished

A human attaches a picture, or a tool produces one, and both end at the same block.

@photo.png extends M19's path rather than growing a second one: the same token scan, the same refusals in the same words — missing, a directory, a credential file, outside the working directory — and then exactly one fork. Bytes that begin with a known image signature spill and come back as an ImageBlock; anything else is decoded as text as before. Compare _refuse with the version on the working state page: it is unchanged. A file that is neither text nor an image is still refused by name.

On the tool side, Read answers a picture with the picture instead of "looks binary; not shown". And ToolFinished gained one optional field carrying the reference, so a watcher on --events can find the file on disk while the bytes never pass through the event stream at all — the same reason blob is on that event already.

Take with you: a second way in should join the first one as early as possible. Here that is one if, and everything downstream never learns there were two.

Stage 2. The half that cost nothing about 20 minutes

Both stops below are folders, not modules. Nothing in src/ changed for either, and that is the claim being tested: the extension formats froze at 1.0, and a capability that fits them should need no code. Read them asking what edgar would have had to grow if the formats were not there.

8Web search, as files

examples/tools/web_search.toml · examples/skills/web-research/SKILL.md

Look for: the three commented variants, and the host that is not there.

Searching the web is an HTTP call with a key in a header, which M3's HTTP-tool format already describes: a request template with the host fixed, arguments filling only path and query, and ${env:NAME} filling headers at call time and scrubbed from whatever comes back. So web search is a TOML file.

The file ships three variants — Brave active, Tavily and a self-hosted SearXNG commented beside it — and no default host, which is PRV-15 doing its job. Who sees your queries is exactly the kind of choice a harness must not make quietly, and the answer is in a file you can read in ten seconds.

The skill is the half that matters. A search tool alone produces a model that answers from snippets, and a snippet is an advertisement for a page, not evidence. The skill says: search, fetch the best two or three, answer with the URLs. It also restates what the harness already enforces — the response is untrusted output, so in auto mode the shell and network calls after it ask before they run.

This page's claim is testable, and it was tested: a subagent with none of this milestone's context, given only the Cookbook and the extension guide and forbidden from opening src/, produced the same host, header and environment variable unaided.

Take with you: the tool is the easy half. The instructions for using it well are the part that makes it worth having.

9git, as files

examples/tools/git-commit.toml · examples/skills/git/SKILL.md · examples/extensions/git-trail/hooks.toml

Look for: the message as one argument, and the two verbs that are missing.

git is a CLI, and M3's command-tool format is an argv template started directly, never through a shell. Four verbs, one file each: look at the tree, read the diff, read the log, commit what is staged. Three are read_only; the fourth writes and goes through the guard like any other write.

Open git-commit.toml and look at one line. The whole message is a single argv element, so a message containing newlines, semicolons and backticks is message text, because no shell ever sees it. Every agent harness that shells out to git commit -m "..." has this bug latent in it.

Then notice the absences, which are the design. There is no git-add: staging is where a human decides what goes in. There is no push, merge or tag: those are the user's calls. And git-log takes a required count, because an argv element naming an absent argument is dropped whole — an optional --max-count would have silently meant the entire history, which is the opposite of a sensible default.

The extension is the post_tool example. It is observation only: fired and forgotten, its output never reaching the model, matched to the one tool worth recording. Read what its script has to do — the event carries the call's outcome, never the tool's output, so it reads the commit back out of git itself. That is the shape of every hook that is not a pre_tool.

Take with you: the argument for declarative extension formats is not that they are elegant. It is that this whole stop is a diff with no code in it.

Before you go: a session attaches a screenshot, runs forty turns, and compaction elides it. The user then asks a question about that screenshot. What does the model see, what did it cost, and where on disk is the picture?
